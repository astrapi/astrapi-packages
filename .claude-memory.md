# astrapi-packages – Claude Memory

Projektkontext für Claude Code. Wird im Repo versioniert, damit es auf jedem PC verfügbar ist.

---

## Was ist astrapi-packages?

Web-UI zum Bauen von Arch-Linux-Paketen (AUR + custom PKGBUILDs) via Docker-Container.
Basis: **astrapi-framework** (FastAPI + Flask via a2wsgi + HTMX).
Langfristig erweiterbar auf Debian/Alpine.

---

## Stack

| Komponente | Details |
|---|---|
| Backend API | FastAPI (`/api/...`) |
| Frontend | Flask + HTMX (`/`) via a2wsgi |
| Persistenz | YamlStorage (astrapi-core) |
| Scheduler | APScheduler via astrapi-core |
| Container | Docker (Arch Linux Bootstrap) |
| Python | ≥ 3.11 |
| Kernabhängigkeit | `astrapi-core>=26.4.1` |

**Einstiegspunkt:** `astrapi_packages._cli:main` → uvicorn → `astrapi_packages._app:create_app()`

## Modul-Konvention (immer einhalten)

Jedes Modul unter `astrapi_packages/modules/<name>/` hat:

| Datei | Inhalt |
|---|---|
| `__init__.py` | `load_modul()` + Scheduler-Registrierung |
| `api.py` | FastAPI-Router (`make_crud_router` oder manuell) |
| `ui.py` | Flask-Blueprint (`make_crud_blueprint` + modulspez. Routen) |
| `jobs.py` | Build-Logik (subprocess, daemon threads) |
| `storage.py` | `store = YamlStorage(KEY)` |
| `schema.yaml` | Felder für CRUD-Modal |
| `modul.yaml` | label, icon, nav_group, card_actions |
| `templates/partials/` | list.html, list_header.html, list_row.html |

**Referenz-Modul:** `modules/docker/` — immer als Vorlage für neue Module verwenden.

**jobs.py-Muster:**
```python
def build(item_id):
    store.update(item_id, {"last_status": "building", "last_built": _now()})
    rc, output = _run(cmd, timeout=3600)
    store.update(item_id, {
        "last_status": "ok" if rc == 0 else "error",
        "last_built": _now(),
        "last_log": output[-20_000:],
    })

def build_async(item_id):
    threading.Thread(target=build, args=(item_id,), daemon=True).start()
```

## Modul: Docker

**Zweck:** Build-Container-Images verwalten (Bauen, Log anzeigen).
**Kein CRUD** – Images sind in `images.yaml` statisch definiert.
**Image-Name:** `ctl/<name>:<tag>` (automatisch zusammengesetzt)
**Status-Felder:** `last_status`, `last_built`, `last_log`

Schlüsseldateien:
- `modules/docker/images.yaml` – Image-Definitionen (arch-builder, debian-builder)
- `modules/docker/dockerfiles/` – Dockerfiles
- `modules/docker/jobs.py` – `build_image()`, `build_image_async()`

## Modul: Pakete

**Zweck:** Paketdefinitionen anlegen und Arch-Pakete bauen.
**Volles CRUD** via `make_crud_router`.

**Felder:**
- `name` (ID), `source_url` (AUR Git-URL), `aur_deps`, `pkg_type` (package/dependency), `enabled`
- Status: `last_status`, `last_built`, `last_log`, `upstream_version`

**Build-Typen:**

| Typ | Ablauf |
|---|---|
| AUR-URL | `docker run <image> <name> <git-url>` |
| GitLab/Custom | PKGBUILD aus DB → Volume-Mount → Container baut lokal |

**Besonderheiten:**
- `dep_graph.py` – Topologische Sortierung (Kahn), Orphan-Detection
- `gitlab_cache.py` – Hintergrund-Cache für GitLab `packages.json` (alle 5 min)
- `_sync_pkgbuild_deps()` – Liest PKGBUILD aus GitLab, aktualisiert deps + upstream_version
- `delete_package()` – Löscht aus Pacman-DB + räumt Orphans auf

**Nach Build:**
```bash
repo-add <repo_path>/<repo_name>.db.tar.gz <paket>.pkg.tar.zst
```

**Einstellungen (settings.yaml):**
- `default_image` – Standard Build-Image (z.B. `ctl/arch-builder:latest`)
- `repo_path` – Pfad zum Pacman-Repo auf dem Host
- `repo_name` – Name der Repo-DB (z.B. `pkgctl`)
- `gitlab_group` – Liste von GitLab-Gruppen/Repos mit packages.json

## Repository HTTP-Server (`api/repo.py`)

**Zweck:** Pacman-kompatibles HTTP-Repository, damit Arch-PCs die gebauten Pakete per `pacman` installieren können.

**URL-Struktur:**

| URL | Inhalt |
|---|---|
| `/repo/` | Distro-Übersicht |
| `/repo/arch/` | HTML-Listing der Arch-Pakete |
| `/repo/arch/<datei>` | Datei-Download (`.pkg.tar.zst`, `.db`, …) |

**pacman.conf auf den Clients:**
```ini
[astrapi]
Server = http://<host>/repo/arch
```

**Distro-Mapping** (`_DISTROS` in `api/repo.py`):
- `arch` → `work_dir/repo/arch/` (Fallback: `work_dir/repo/` wenn Unterordner fehlt)
- Weitere Distros (debian, …) dort eintragen wenn nötig

**Registrierung:** Router wird in `api/fastapi_app.py` via `app.include_router(repo_router)` eingebunden.

## Scheduler

Aktionen werden in `__init__.py` des Moduls registriert:
```python
from astrapi.core.modules.scheduler.engine import register_action
register_action("pakete.update_all", "Pakete: Aktualisieren", update_all_packages, ...)
```

Verfügbare Jobs:
- `docker.build_arch_builder` – arch-builder aktualisieren
- `pakete.update_all` – Alle Pakete auf Aktualität prüfen
- `pakete.mark_orphans` – Verwaiste Abhängigkeiten markieren
